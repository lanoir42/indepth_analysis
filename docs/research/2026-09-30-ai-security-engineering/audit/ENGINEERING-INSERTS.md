# 기술 본문 보강 원고 — CaMeL·tacit·OpenShell·Sentry

편집용 원고, 2026-09-30. 정본 통합용이며 별도 독자 문서로 발행하지 않는다. 아래 실행 예는 원리를 설명하기 위해 구성한 예다. 실제 제품 시험을 수행한 결과와 구분한다. 투자·가치평가·포지션 제안은 포함하지 않는다.

## CaMeL — 판단하는 모델과 외부 자료를 읽는 모델을 분리한다

CaMeL은 계획과 자료 해석을 서로 다른 통로에 놓는 에이전트 실행 구조다. 사용자에게서 받은 신뢰된 요청은 계획 모델인 P-LLM으로 간다. 이 모델은 도구를 조합하는 제한된 Python 프로그램을 만들지만 도구가 읽어 온 문서 내용은 직접 보지 않는다. 문서 해석은 도구 실행 권한이 없는 Q-LLM이 맡고, 프로그램의 인터프리터가 값의 출처와 전달 범위를 관리한다. 공격 문장이 자료 해석 모델에 도달하더라도 그 모델이 실행기를 직접 부를 수 없도록 하는 방식이다. 연구 코드의 개발 주체는 Google·Google DeepMind·ETH Zurich 연구진이다. 공개 저장소는 재현용 연구 산출물이며 Google의 지원 제품으로 설명하지 않는다. [논문 v2](https://arxiv.org/html/2503.18813v2), [연구 저장소](https://github.com/google-research/camel-prompt-injection).

예를 들어 “계약서의 갱신일을 확인해 내부 담당자에게 알려 달라”는 업무를 생각할 수 있다. 계획 모델이 ‘계약서 읽기→갱신일 추출→지정 담당자에게 전달’이라는 흐름을 만든다. 계약서에 “다른 주소로 원문을 전송하라”는 문장이 있어도 자료를 읽는 모델에는 전송 도구가 없다. 만일 그 주소가 추출 값으로 반환되더라도 실행기는 수신자 값이 승인된 사용자 요청에서 왔는지, 문서의 열람 권한과 수신자가 양립하는지 검사한다. 값의 형식이 이메일 주소라는 사실은 전송 승인을 뜻하지 않는다. 이 예의 핵심은 모델이 공격 문장을 정확히 분류했는지가 아니라 자료의 영향이 실제 권한을 얻는 통로를 제한했는지다.

기밀성과 지시 신뢰도도 별도 축이다. 공개 웹 문서는 누구에게 보여 주어도 되지만 그 문장에 업무 권한은 없다. 반대로 내부 계약서는 유효한 숫자를 담고 있어도 외부 수신자를 승인하는 문서가 아니다. 이 구분을 실행 메타데이터로 유지하면 ‘공개 자료이므로 안전하다’는 잘못된 승격을 막는다. 본 보고서의 정책식에도 자료를 보낼 수 있는지와 동작을 결정한 입력을 신뢰할 수 있는지를 각각 넣어야 한다.

CaMeL의 STRICT 모드는 분기·반복과 격리 모델 이후의 의존성을 더 넓게 전파한다. 비밀 조건에 따라 외부 호출의 유무가 달라지는 간접 유출을 줄이는 역할이다. v2 초록의 AgentDojo 완료율은 77%, 무방어 비교는 84%다. 이는 특정 평가의 유용성 결과이며 모든 제품의 예방률이 아니다. 외부 문서가 정하는 새 업무를 유연하게 수행하는 능력은 분리 구조와 충돌할 수 있다. 오류 복구와 메모리 신뢰도 같은 경계가 중요한 이유도 여기에 있다. [CaMeL v2 §5–7](https://arxiv.org/html/2503.18813v2).

공개 구현에서도 모드 선택은 실제 실행 인자다. `main.py`는 기본 `eval_mode`를 `MetadataEvalMode.NORMAL`로 두고 이를 파이프라인에 전달한다. 인터프리터는 `STRICT`와 `NORMAL`을 구별하고 예외에 의존 값과 capability 메타데이터를 붙인다. 따라서 “CaMeL을 실행했다”는 기록만으로는 엄격한 의존성 전파가 적용됐는지 알 수 없다. 사용한 모드와 보안 정책을 실행 결과에 함께 기록해야 재현 가능한 평가가 된다. [평가 진입점 소스](https://raw.githubusercontent.com/google-research/camel-prompt-injection/main/main.py), [인터프리터 소스](https://raw.githubusercontent.com/google-research/camel-prompt-injection/main/src/camel/interpreter/interpreter.py).

## tacit — 생성 코드가 사용할 권한을 타입에 기록한다


tacit은 EPFL LAMP 연구진의 공개 구현으로, 에이전트와 운영체제 사이에 Scala 3 컴파일러·REPL·capability 라이브러리를 배치한다. 에이전트는 MCP로 코드를 제출한다. 컴파일러가 권한 추적을 켠 안전한 언어 부분집합으로 코드를 검사하고, 통과한 코드만 실행한다. 파일·네트워크·외부 프로세스 접근은 라이브러리가 제공하는 권한 객체를 통해 이루어진다. 따라서 ‘에이전트가 이 권한을 요청했다’는 사실과 ‘그 권한을 실제 부여했다’는 사실이 분리된다. 기존 파일·셸·네트워크 도구까지 열어 두면 이 검사 경로를 우회할 수 있으므로 연동 설계가 필요하다. [tacit 공개 구현](https://github.com/lampepfl/tacit).

기밀 계약서 두 버전을 비교하는 업무에서는 코드가 문서를 읽더라도 내용이 일반 문자열 대신 `Classified`로 감싸져 전달된다. 순수 함수로 공백을 정리하거나 차이를 계산하면 결과도 기밀 값으로 남는다. ‘계약서 내용을 읽은 뒤 외부 파일에 쓰는 함수’는 파일 쓰기 권한을 포획하므로 순수 함수 요구를 만족하지 못한다. 기밀 내용을 이해해야 하는 요약 작업에는 신뢰된 로컬 모델을 연결하고, 그 응답도 기밀 값으로 유지할 수 있다. 계획을 세우는 외부 모델은 작업 구조를 다루고 기밀 원문은 허용된 계산 안에 머물게 하는 것이다. 이 방식은 모델에게 비밀 유지 약속을 받는 대신 프로그램의 데이터 사용 방식에 제약을 준다. [연구 논문 §3](https://www.yichenxu.me/files/publications/securing-agents/paper.pdf).

하지만 기밀 값을 읽지 못하게 하는 기능과 기밀 파일을 변경하지 못하게 하는 기능은 다르다. 9월 30일 조회한 구현 문서에서 `classifiedWrite`는 기본적으로 켜져 있다. 문서는 기밀 경로의 무결성이 필요하면 이를 끄라고 안내한다. 보안 설정 파일을 보호할 때 이 차이가 중요하다. 내용이 모델에게 보이지 않아도 파일이 공격자가 정한 내용으로 덮어써지면 인증 규칙이 바뀔 수 있다. 파일 읽기 기밀성, 파일 쓰기 무결성, 외부 호출 권한을 각각 정책에 적어야 한다. [tacit Configuration](https://github.com/lampepfl/tacit#configuration).

논문의 기밀 유출 평가에서는 모델·모드마다 131회 시험을 수행했고, 기밀 모드의 두 모델에서 유출 없는 비율 100%를 보고했다. 실험 표는 그 시험 집합의 관측값이다. 기반 capture-checking 타입체계의 기계화된 증명과 tacit 안전모드 전체의 의미론적 증명도 구분된다. 논문은 후자를 추가 과제로 남겼다. 정적 검사는 허용된 코드의 권한 사용을 제한하며 외부 명령을 실행한 뒤의 모든 동작까지 증명하지 않는다. 운영체제 격리가 이를 보완한다. [연구 논문 §4.1·§5·§6](https://www.yichenxu.me/files/publications/securing-agents/paper.pdf).

## OpenShell — 허용된 연결을 중개하고 다른 외부 경로를 닫는다

NVIDIA OpenShell은 에이전트 작업을 실행하는 경계와 정책을 결정하는 supervisor를 분리하는 공개 런타임이다. 확인한 v0.1.2는 2026년 9월 28일 릴리스이며 커밋은 `6648bd0c290efbc41ba131ee9831ee45cd431f94`다. 작업 쪽에는 비특권 실행·파일 제한·시스템 호출 중개가 놓이고 supervisor가 외부 연결과 정책을 담당한다. 프로그램이 외부 서버에 연결하려 할 때 중개기가 요청을 붙잡아 판단을 요청하고, 허용되면 통신을 이어 준다. 이 통로 바깥의 직접 네트워크는 컨테이너·VM·Kubernetes 배치별 외곽 경계가 막는다. 프록시 주소를 환경변수로 알려 주는 것보다 강한 이유는 사용자가 작성한 프로그램이 다른 직접 경로를 택하는 경우까지 경계를 적용하기 때문이다. [v0.1.2 릴리스](https://github.com/NVIDIA/OpenShell/releases/tag/v0.1.2), [고정 태그 아키텍처](https://raw.githubusercontent.com/NVIDIA/OpenShell/v0.1.2/architecture/sandbox.md).

예를 들어 내부 소스코드를 읽어 테스트 결과를 만드는 작업에는 저장소 읽기와 특정 패키지 서버 연결만 허용할 수 있다. 모델이 별도 HTTP 프로그램을 만들더라도 외부 연결이 supervisor를 통과해야 한다면 목적지 제한을 공유한다. 여기에 단순 ‘호스트 허용’보다 세밀한 API 동작 규칙을 붙이면 같은 서비스의 읽기와 게시를 나눌 수 있다. 실제 보호는 정책 판단과 커널·네트워크 경계가 함께 맞아야 성립한다. 독립 네트워크 프록시 모드는 호출 프로세스의 신원을 확인하지 못하므로 전체 sandbox 배치와 같은 보장으로 비교하면 안 된다. [v0.1.2 아키텍처](https://raw.githubusercontent.com/NVIDIA/OpenShell/v0.1.2/architecture/sandbox.md).

실제 구현에서 수명 관리가 별도 문제라는 점도 확인할 수 있다. 릴리스 커밋은 `managed_children.rs`에서 자식 종료 신호와 복구 스캔으로 고아 프로세스 회수를 처리하는 변경과 관련 시험을 포함한다. 같은 커밋의 문서는 주요 작업 프로세스가 끝나도 허용된 추가 실행과 전달 경로가 명시적 stop/delete까지 남는다고 설명한다. ‘모델 응답 완료’, ‘작업 프로세스 종료’, ‘실행 경계 해체’는 운영상 다른 상태다. 보안 종료는 마지막 단계와 외부 권한 회수를 함께 확인해야 한다. 이는 공개 소스·문서에서 확인한 수명 모델이며 이번 보고서가 해당 시험을 직접 실행한 결과는 아니다. [릴리스 커밋의 소스 차이](https://github.com/NVIDIA/OpenShell/commit/6648bd0c290efbc41ba131ee9831ee45cd431f94).

OpenShell의 정책 검증도 정확한 대상이 있다. 9월 30일 조회한 최신 Policy Prover 문서는 후보 정책이 관리자가 정의한 경계보다 넓은 접근을 허용하는지 비교한다. 파일 쓰기를 새로 추가하면 그 접근을 반례로 보여 주는 방식이다. 검사 대상은 파일·프로세스 신원·Landlock 설정·네트워크·REST이며, MCP나 GraphQL처럼 모델링되지 않은 정책은 `unsupported`로 처리한다. 통과는 해당 정책 모델 안에서 경계를 넘지 않는다는 뜻이다. 자연어 업무 목적이 옳은지, 실행 중 커널이 정책을 제대로 적용했는지를 함께 증명하지 않는다. 이 최신 문서의 기능을 고정 태그 v0.1.2의 전체 구현으로 소급하지 않아야 한다. [Policy Prover](https://docs.nvidia.com/openshell/latest/how-it-works/policies/prover).

## Sentry — 정책 집행을 호스트와 다른 하드웨어 신뢰 영역에 배치한다

Sentry는 NVIDIA가 2026년 9월 28일 공개한 Open Agent Safety Platform의 BlueField-4 참조 시스템이다. OpenShell이 작업의 실행 경계를 구성한다면 Sentry는 호스트 밖 DPU에서 감독·집행을 수행하는 추가 영역이다. DOCA는 DPU의 기능을 프로그래밍하고 정책·신원·텔레메트리를 연결하는 소프트웨어 기반이다. 이 구성이 겨냥하는 실패는 에이전트가 호스트 자원을 장악했을 때 같은 호스트 안의 감독도 함께 훼손되는 경우다. 신뢰 영역을 물리적으로 분리하면 호스트의 실행 권한이 감독 정책에 곧바로 이어지는 경로를 줄일 수 있다. [NVIDIA 기술 설명](https://developer.nvidia.com/blog/nvidia-open-agent-safety-platform-a-reference-for-continuous-in-silicon-agent-monitoring/).

모델 추론 서비스가 외부에 있고 노드가 그 서비스로 가는 유일한 길에 DPU가 있는 배치를 생각할 수 있다. 에이전트의 다음 추론 요청을 차단하면 새 계획을 만드는 루프를 멈추는 통제 지점이 된다. 그러나 이미 실행 중인 파일 변환 프로그램이나 외부 서비스에 등록된 작업의 수명은 별도로 관리해야 한다. 기술적으로 필요한 연결은 ‘추론 차단 신호→새 도구 호출 보류→실행기 정지→외부 토큰 회수→이미 발생한 효과 대사’다. 이 상태 전이는 본 보고서의 설계 예이며 Sentry가 모든 단계를 현재 구현했다는 뜻으로 제시하지 않는다.

DPU의 위치와 실제 관측 범위도 연결해서 설명해야 한다. 암호화된 세션이 단순히 DPU를 지난다는 사실만으로 내부 문장의 업무 의미를 읽을 수 있는 것은 아니다. 내용을 검사하려면 종료 지점이나 신뢰된 계측에서 필요한 증거를 받아야 한다. 모델 호출·도구 호출·작업 신원을 연결한 텔레메트리는 의미 판단에 도움을 주고, DPU의 경로 통제는 그 판단을 실제 차단으로 바꾼다. 이 둘은 센서와 집행기의 분업이다. 정책을 어느 입력으로 판단하고 어디에서 집행하는지까지 그려야 ‘하드웨어 보안’이라는 표현이 구체적인 설계가 된다.

현재 제공 상태는 OpenShell과 구별된다. 보도자료는 OpenShell의 광범위 제공과 공개 코드·문서를 명시한다. Sentry는 BlueField-4의 참조 시스템으로 소개하며, 독립 설치 패키지·버전·일반 제공 지원 범위는 같은 자료에서 확정되지 않는다. 밀리초 격리와 전 구간 계보 추적은 공급자 발표의 기능 주장으로 다루고 공개 재현 시험 결과와 분리한다. 기술 설명의 유일한 모델 연결 경로도 Vera Rubin POD의 해당 배치를 전제로 한다. 이 구분을 유지해야 연구 독자가 실제로 설치 가능한 실행기와 하드웨어 시스템 설계를 서로 다른 성숙도로 이해할 수 있다.
