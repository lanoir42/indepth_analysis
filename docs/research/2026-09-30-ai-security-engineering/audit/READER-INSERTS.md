# READER-INSERTS — 기술 해설 보강 원고

편집자 안내: 아래 두 절은 본문에 통합할 수 있는 원고다. 정본은 수정하지 않았다. 2026-09-30에 AI Control 원논문 v3와 Factor(T,U) v1의 실험 설정·결과·방법론 한계를 직접 재조회했다. 투자·가격·밸류에이션은 포함하지 않는다.

## 보강 1. AI Control — 강한 모델을 쓰되 결과 채택권을 분리하는 프로토콜

### 코드를 생성하는 모델과 채택하는 절차를 분리한다

Greenblatt 등의 실험에서 U는 강하지만 의도적으로 잘못된 코드를 낼 수 있는 GPT-4, T는 위해 의도가 없다고 가정한 GPT-3.5다. 고급 감사 H는 사람의 대역인 별도 GPT-4 채널이며 예산은 과제의 2%다. 신뢰는 무오류라는 뜻이 아니다.

공격 목표는 통상 테스트를 통과하면서 특정 입력에서 틀리는 코드를 제출시키는 것이다. APPS 1,500문제에서 얻은 응답을 재표집해 5,000문제 시나리오를 추정했다. 안전성은 전체 시나리오에서 백도어를 한 번도 제출하지 않을 확률이다. 유용성은 정답률을 T=0, 정상 U=100으로 환산한다. [실험 설정·지표](https://arxiv.org/html/2312.06942v3#S2)

| 프로토콜 | 처리 절차 | 안전성 / 환산 유용성 |
|---|---|---|
| 사전 감사 | 처음 2%만 감사한 뒤 U 사용 | 15% / 100% |
| Trusted monitoring | U 생성→T 의심도→상위 2% 감사 | 62% / 97% |
| Defer to trusted 20% | 고의심 구간은 감사, 중간 구간은 T가 독립 재작성 | 92% / 83% |
| Trusted editing 20% | 중간 구간은 T가 U의 코드를 참고해 수정 | 92% / 94% |

감사에서 위해가 드러나면 이후 U 사용을 중단한다. 사전 감사는 드문 공격을 놓치지만, 지속 감시는 공격 기회마다 위험을 만든다. 편집은 강한 모델의 유용한 구조를 보존하려는 방식이다. 원시 정답률은 T 22%, U 54%여서 환산 유용성 94%는 정답률 94%가 아니다. 동일 문제로 설계를 조정한 점과 강한 감사 가정은 일반화 범위를 제한한다. [절차·결과 표7](https://arxiv.org/html/2312.06942v3#S3.SS5)

### 작업을 나누면 무엇이 좋아지고 무엇이 나빠지는가

Factor(T,U)는 신뢰된 분해기가 하위 과제와 결합 코드를 만들고, U가 분리된 문맥에서 하위 과제를 구현하며 T가 각각을 감시하는 방식이다. 핵심 가설은 작은 과제가 감시기에 더 이해하기 쉽다는 것이다.

실험은 APPS-verified 500문제를 절반씩 학습/시험용으로 나눴다. 과제의 99%에는 단위시험이 하나뿐이었다. U=GPT-4.1 Nano, T=Llama 3.1 8B-Instruct다. 약한 T의 분해 성능이 낮아 안전성 실험에는 신뢰된 o3-mini 분해기 D를 별도로 허용했다. 감사는 정상 운용에서 2%가 선택되도록 임계값을 정하며, 선정된 위해는 완전히 발견한다고 가정한다. 따라서 주요 안전성 수치는 Factor(D,U)의 결과다. [설정](https://arxiv.org/html/2512.02157v1#S2)

| 방식 | 평균 하위 과제 수 | 안전성 |
|---|---:|---:|
| 기본 신뢰 감시 | 분해 없음 | 41% |
| 낮은 분해도 | 2.0 | 63% |
| 중간 분해도 | 3.0 | 56% |
| 높은 분해도 | 3.5 | 49% |

안전성은 1,000개 원과제 배포를 모형화한 값이다. 분해는 감시기의 공격 식별을 개선했지만 더 잘게 나눌수록 성적이 좋아지지는 않았다. 문맥을 숨겨 공격 자체를 어렵게 한다는 가설은 강한 악용 탐색기를 사용했을 때 지지되지 않았다. T가 직접 분해하면 환산 유용성은 −63%로 T 단독보다 낮았다. 안전성 개선과 실용성 입증을 함께 읽어야 한다. [§3·부록J](https://arxiv.org/html/2512.02157v1#S3)

### 업무 설계에 적용할 때의 해석

다음은 위 논문의 수치를 새 업무에 대입한 결과가 아니라 본 보고서의 설계 해석이다. 예를 들어 자료 분석과 게시를 나누면 분석기는 결론의 품질을 높이는 데 집중하고, 게시기는 승인된 결과를 정해진 목적지에 보내는 좁은 동작만 수행할 수 있다. 게시기의 질문은 “분석 전체가 현명한가”보다 “이 버전의 문서를 이 수신자에게 보내도록 승인받았는가”가 된다. 후자는 내용 해시·수신자·권한으로 검사할 수 있다.

다만 하위 과제에 셸·네트워크 권한을 주면 그 과제가 끝나기 전에 외부 효과가 생길 수 있다. 최종 결과를 합칠 때 검사하는 절차만으로는 그 효과를 회수할 수 없다. 결과물 검토와 실행 전 통제가 필요한 위치를 각각 정해야 한다. 아래 추적은 이 차이를 구체화한다.

## 보강 2. 문서 요약에서 게시까지 — 여덟 단계에서 다른 통제가 작동한다

아래는 **저자가 만든 설명용 시스템 설계**다. 특정 제품이 이 구성을 그대로 제공한다거나 실제 성능 시험을 통과했다는 뜻은 아니다. 목표는 서로 다른 보안 기술이 동일 업무의 어느 시점에서 무엇을 판단하는지 보여 주는 것이다.

업무는 “지정한 외부 PDF와 내부 전망치를 읽고 내부 초안을 만든 뒤, 책임자가 승인한 공개본을 회사 홈페이지에 게시”하는 것이다. 입력 PDF는 비신뢰 자료, 내부 전망치는 제한 자료다. 사용자는 초안 작성까지 먼저 승인한다. 게시 권한은 공개본·목적지가 확정된 다음 별도로 발급한다.

```text
작업 계약 → 외부 PDF 격리 처리 → 자료 추출/요약 → 내부자료 조회
         → 등급을 보존한 결합 → 공개본 승인 → 실제 게시 → 종료/대사
```

### 1단계: 사용자 요청을 작업 계약으로 고정한다

실행기는 작업 J의 주체, 허용 PDF, 내부자료 식별자, 초안 저장 위치, 만료 시각을 기록한다. 모델에 부여하는 초기 도구는 읽기와 내부 초안 쓰기다. `publish` 동작은 아직 허용하지 않는다. 서비스의 모든 자료를 읽는 사람 계정의 장기 토큰 대신 J에 필요한 접근만 전달하는 구성을 가정한다.

여기서 신원 통제는 요청자가 누구인지 확인하고, 권한 통제는 J가 어느 자원에서 어떤 동작을 할 수 있는지 결정한다. 모델의 자연어 해석을 이 계약을 수정하는 권한으로 사용하지 않는다. 계약 변경은 사용자 승인 경로에서 처리한다.

### 2단계: 외부 PDF를 제한된 처리기에서 연다

PDF 처리 프로세스에는 원본 입력과 임시 출력만 보이고 내부 전망치·게시 키는 보이지 않게 한다. 파일 접근 제한과 시스템 호출 제한으로 처리기의 동작 범위를 줄이고, 네트워크를 사용할 이유가 없는 이 단계에서는 통신을 차단한다.

이 통제는 PDF 파서 결함으로 코드가 실행되는 상황의 피해 경로를 줄인다. PDF 안의 그럴듯한 자연어 지시가 모델을 설득하는 문제는 다음 단계의 대상이다. 같은 PDF에서 출발해도 바이너리 파서의 침해와 자연어 지시의 오인에는 다른 통제가 개입한다.

### 3단계: 추출한 문장을 자료로 취급한다

출력 텍스트에는 원본 문서 식별자·버전·외부 출처 표시를 붙인다. 분류기는 업무와 무관한 지시나 외부 전송 요구를 탐지할 수 있다. 추가로 모델이 반환할 결과를 요약·근거 위치 같은 자료 구조로 제한하고, 반환값이 새로운 도구나 수신자를 등록하는 경로를 없앤다.

분류기가 놓친 지시가 있더라도 다음 도구 호출은 1단계 계약을 다시 통과해야 한다. 분류기는 위해 제안을 줄이는 역할을 맡고, 실행기는 제안이 실제 권한을 얻는 순간을 통제한다. 이 설계는 신뢰할 요청에서 정한 실행 흐름과 비신뢰 자료의 처리를 나누고 값의 흐름을 추적하는 CaMeL의 문제 설정을 참고했다. 아래 전체 시스템의 제품 보장은 아니다. [CaMeL 논문](https://arxiv.org/html/2503.18813v2)

### 4단계: 내부자료를 조회할 때 권한과 등급을 함께 받는다

내부자료 커넥터는 J가 지정된 전망치를 읽을 수 있는지 검증한 뒤, 내용과 함께 `제한`, 자료 버전, 접근 출처를 반환한다. “같은 사용자의 토큰이므로 모든 문서 허용”이라는 판단을 피하려면 실제 자료 서버가 작업 범위 또는 그에 대응하는 좁은 접근 권한을 확인해야 한다.

캐시를 이용하는 경우에도 현재 접근권을 확인한다. 자료의 권한이 취소되었는데 이전 요약이 검색으로 다시 돌아오면 원본 접근 통제만으로는 업무 전체를 제한할 수 없다. 이 설계에서는 캐시 항목에도 자료 식별자와 파생 관계를 붙여 권한 변경의 영향을 찾을 수 있게 한다.

### 5단계: 결합 결과에 자료의 제한을 전파한다

공개 PDF 요약과 제한 전망치를 결합한 내부 초안도 제한 등급으로 취급한다. 내부 수치를 직접 복사하지 않고 서술로 바꾸어도 파생 관계를 유지한다. 실행기는 이 초안을 내부 저장소에 쓰는 것은 허용하고 공개 목적지에 보내는 것은 보류한다.

여기서 단순 DLP는 특정 숫자·표현의 출현을 찾을 수 있고, 정보 흐름 통제는 그 표현이 사라졌어도 결과가 제한 자료에서 파생되었다는 사실을 사용한다. 양자는 서로 다른 신호다. 모델이 스스로 “기밀이 없다”고 선언하는 것만으로 등급을 낮출 수 없게 한다.

### 6단계: 공개본 승인으로 허용 범위를 좁혀 추가한다

책임자는 내부 초안 전체를 무조건 공개 허용하는 대신, 공개 가능한 근거만으로 만든 버전 P를 검토한다. 승인 기록은 `작업 J + P의 내용 해시 + 지정 홈페이지 경로 + 게시 동작 + 만료`에 결합한다. 이 단계에서 제한을 낮추는 결정과 그 책임을 기록한다.

이후 모델이 문장을 고치거나 수신자를 변경하면 해시 또는 목적지가 달라져 재승인이 필요하다. 이 방식은 승인 시점의 안전한 화면과 실제 전송 내용을 연결하려는 저자 설계다. 내용이 계속 변하는 협업 문서라면 버전 고정 스냅샷이나 서버 측 조건부 쓰기 같은 구현이 필요하다.

### 7단계: 실제 외부 전송 직전에 정책을 집행한다

게시 실행기는 현재 계약·회수 상태·승인 해시·목적지를 검증하고, 실제 전송 바이트가 승인 버전과 일치할 때만 게시 자격증명을 사용한다. 모델 프로세스에는 자격증명을 전달하지 않는 구성을 가정한다. 운영체제/네트워크 통제로 모델이 게시 API를 직접 호출하는 대체 경로도 제한한다.

독립 프록시나 DPU가 있다면 모든 관련 통신이 그 경로를 통과하는지 먼저 확인해야 한다. 암호화된 통신에서 해당 장치가 목적지만 보는지, 애플리케이션에서 검증한 동작 정보를 받는지, 복호화 지점에서 내용을 보는지에 따라 판단 가능한 범위가 달라진다. “DPU를 사용한다”는 사실만으로 승인 해시 검증까지 수행했다고 볼 수 없다.

### 8단계: 성공·실패를 대사하고 남은 권한을 끝낸다

게시 응답이 시간 초과여도 서버에서 게시가 성공했을 수 있다. 실행기는 작업 식별자로 실제 결과를 조회한 뒤 재시도를 결정한다. 재전송이 필요한 경우 동일 멱등성 키를 사용한다는 설계를 둔다. 로그에는 제안, 승인, 실행 시작, 외부 시스템의 완료를 서로 다른 사건으로 남긴다.

종료 시에는 새 호출을 막고 토큰·대기 작업·예약 게시·임시 캐시를 정리한다. 중간에 회수 요청이 들어오면 이미 완료한 게시와 아직 미완료인 동작을 구별한다. “프로세스가 종료되었다”는 상태와 “더 이상 외부 효과가 생기지 않는다”는 상태가 일치하는지 확인해야 한다.

### 동일 업무에서의 통제 비교

| 통제 | 직접 다루는 질문 | 이 예에서 개입하는 시점 |
|---|---|---|
| 입력/출력 분류기 | 이 문장·결과에 공격 또는 정책 위반 징후가 있는가 | 자료 해석 전후 |
| 작업 신원·최소권한 | 이 작업이 이 자료·동작에 접근할 권한이 있는가 | 조회·저장·게시 호출마다 |
| 정보 흐름 추적 | 제한 자료에서 파생된 값이 허용되지 않은 목적지로 가는가 | 자료 결합·외부 전달 |
| OS 격리 | 프로세스가 보이는 파일·자원·시스템 호출 범위는 무엇인가 | 파일 처리와 모델/도구 실행 중 |
| 독립 실행기·네트워크 집행 | 모델이 제안한 동작을 실제로 허용할 것인가 | 외부 효과가 생기기 직전 |
| 사람 승인과 버전 결합 | 어떤 내용을 어디에 보낸다는 의사결정인가 | 공개본 확정 및 실행 재검증 |
| 회수·대사·복구 | 새 효과를 멈췄고 기존 효과의 실제 상태를 아는가 | 중단·오류·종료 이후 |

이 기준 사례에서 통제를 시험한다면 같은 정상 업무를 완료하는지와 함께, 외부자료의 전송 지시, 파서 프로세스의 예기치 않은 파일 접근, 승인 이후 문서 변경, 게시 도중 권한 회수, 응답 유실 후 재시도라는 변형을 각각 넣는다. 산출물은 단순 차단률보다 **어느 경계에서 어떤 근거로 막았으며 정상 결과와 외부 상태가 어떻게 남았는지**를 보여 주는 실행 기록이어야 한다.
