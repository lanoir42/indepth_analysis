# 사이버보안 발표 Advisor 설계

작성일: 2026-10-02. 검토 대상: `source/20261006_사이버보안.pdf`, 텍스트 추출본 및 page-01~19.png 전쪽. 역할: 서사·집필 요구·질문·정정 후보 설계. 최종 독자용 본문 미집필, 향후 독립 감사 유지.

## 1. 논지와 범위

발표의 중심은 **외부 자료를 해석하는 모델과 권한을 행사하는 실행기의 결합에서 생기는 실패, 그리고 이를 줄이는 통제의 작동 원리**. 기술 설명의 일관된 예제는 ‘외부 PDF와 내부 전망치를 읽어 보고서 초안을 만드는 에이전트’로 고정. 공격 문서가 외부 게시를 유도하는 경우를 입력→계획→도구 호출→권한 검사→전송→회수 순서로 추적하면 L0~L5·ID 표와 개별 제품의 역할을 하나의 업무에 연결 가능.

사용자의 앞선 기술·과학·공학 중심 요구는 유지. 이번 PDF의 후반 투자 장표는 빠뜨리지 않되, 산업·투자 결론을 기술 원리의 필연적 귀결로 확장하지 않을 것. 통제 공백의 존재→고객 구매의사→공급자 가격·매출→주가 반응은 각각 추가 근거가 필요한 단계. p13~17은 원장표의 주장, 그 주장을 성립시키는 가정, 현재 근거로 가능한 판단을 설명하는 약 8분 구간으로 한정. 실제 종목·옵션의 매매 제안 확대 금지.

기술부 핵심 긴장 세 가지:

| 긴장 | 설명해야 할 원인 | 도달할 결론 |
|---|---|---|
| 유용한 자율성과 제한된 권한 | 업무 진행에는 문서·API 접근이 필요하고, 같은 권한이 악성 지시에도 사용 가능 | 업무·대상·수신자·시간·예산을 묶은 작은 권한을 실행 시 검사 |
| 의미 판단과 기계 집행 | 위험한 의도 판별은 불확실하고 정책 적용은 명시적 규칙으로 수행 가능 | 분류기의 위험도와 실행기의 허용 조건을 별도 설계, 둘의 오류를 별도 측정 |
| 각 통제의 강점과 남는 경로 | 필터·타입·VM·DPU는 볼 수 있는 정보와 막을 수 있는 동작이 다름 | 위협·업무·통제 지점을 먼저 정하고 검증 조건을 맞춘 비교 |

집필 통과 기준은 독자가 단일 본문만으로 ‘어떤 입력이 어떤 권한을 거쳐 어떤 상태를 바꾸며, 어느 통제가 왜 그 변화를 막는가’를 설명할 수 있는지. 제품명·링크·질문 목록만으로 설명 충족 처리 금지.

## 3. 단일 아티클 집필 계약

독서 단위는 한 파일. 도입·전체 논지, 19쪽 순서에 맞춘 발표 대본, 필요한 기술 심화 설명, 예상 질문의 답, 참고문헌을 한 파일에 배치. 각 쪽에서 대본과 심화 설명을 구분하여 발표자는 낭독 범위를 알 수 있고 학습자는 같은 파일에서 원리까지 이해 가능하도록 구성. 단순 목차 파일과 별도 장별 파일로 독서를 분산시키지 않을 것.

대본은 실제 말할 문장으로 작성. ‘여기서 CaMeL을 설명한다’ 같은 집필 지시문 금지. 심화 해설은 용어 정의→동일 업무의 입력/상태/출력 예→집행 원리→막히는 경로와 남는 경로→평가 조건의 연결을 요구. 질문 답변은 ‘추가 확인 필요’로 끝내지 말고 공개된 원리·조건부 해석·판단에 미치는 영향을 설명할 것.

| 심화 단위 | 빠질 수 없는 내용 | 흔한 얕은 설명의 결함 |
|---|---|---|
| 프롬프트 주입 | 신뢰하지 않는 문서의 명령이 사용자 지시와 같은 처리 문맥에 들어오는 과정, 유효 토큰이 악성 목적에도 작동하는 사례 | ‘모델이 속는다’ 한 문장으로 원리 생략 |
| 참조감시기 | 모든 중요 경로 중개·변조 저항·검증 가능성, 빠진 셸/네트워크/하위 도구 우회 경로 | ‘독립 실행기’라는 명칭을 독립 보장으로 취급 |
| 출처 표식 | 표식이 어디서 생성되고 변환 후 보존되는지, 모델 규칙 준수 의존성과 엔진 정책 연결 차이 | 출처 표시만으로 정보흐름 집행 달성 주장 |
| CaMeL | 신뢰도 낮은 콘텐츠를 처리하는 경로와 계획 경로의 분리, 값에 붙은 권한·출처 정보, 인터프리터의 도구 실행 검사 | Google 제품 필터로 축약 |
| tacit | 코드의 타입/권한 조건이 무엇을 금지하는지, 생성 코드 검사·실행 경계·기밀 계산의 역할, 증명의 범위 | 타입 안전성을 업무 목적 안전성으로 확장 |
| 이력 정책 | 읽은 자료 이후 전송 금지 같은 시간·관계 조건, 관측 누락·우회 도구·정책 충돌 | 매 호출 독립 allowlist와 같은 기술로 처리 |
| 격리·DPU | 커널/VM의 파일·프로세스 경계와 DPU의 네트워크 경계, 관리 영역 독립, 허용된 TLS/API에 남는 의미 공백 | 하드웨어가 프롬프트 의도를 판독한다고 오해 |
| 권한 회수·복구 | 파생 토큰·예약 작업·진행 중 요청의 종료, 멱등 키가 막는 중복, 외부 전송 후 비가역 효과 | 토큰 삭제만으로 업무 상태 원상복구 주장 |
| 실험 수치 | 실험 단위·모델·환경·공격 예산·정상 과제 성공률·기준선과 적용 한계 | 공급자 일치율을 현업 사고 방지율로 사용 |

기존 보고서의 해설·결론은 근거 후보. 같은 문장을 재사용할 때도 이번 PDF의 주장과 원자료를 대조. 특히 과거 NAV 비용 오류·잘못된 회사 분류·확정되지 않은 기술 제공 상태를 상속하지 않을 것.

## 4. 예상 기술 질문 22개와 답변 필수 요소

최종 아티클에서는 아래 요소를 실제 답변 문장으로 풀어 작성. 질문 수를 채우기 위한 중복 답변 금지.

| 번호 | 질문 | 답변에 필요한 설명 |
|---|---|---|
| T01 | 프롬프트 주입과 일반적인 잘못된 답변은 어떻게 다른가 | 외부 자료에 공격자가 넣은 지시의 신뢰 경계 침범과 모델 자체 오류 구별. 두 원인이 같은 외부 전송으로 수렴하는 사례 |
| T02 | 권한 있는 사용자가 정상 API를 쓰는데 왜 차단해야 하는가 | 인증은 주체 확인, 인가는 구체 동작 허용, 업무 승인은 목적·대상·수신자 제약. 유효 토큰의 범위가 사용자 요청보다 넓을 수 있음 |
| T03 | 시스템 프롬프트에 금지 규칙을 쓰면 충분한가 | 모델의 해석 경로와 실제 실행 경로의 차이. 모델이 금지 위반 도구 호출을 제안해도 실행기가 거절하는 예 |
| T04 | Zero Trust와 참조감시기는 같은 개념인가 | 지속적인 명시적 검증의 설계 원칙과 완전 중개·변조 저항·검증 가능성을 갖춘 집행 구조의 관계. 표어가 구현 보장을 대신하지 못하는 이유 |
