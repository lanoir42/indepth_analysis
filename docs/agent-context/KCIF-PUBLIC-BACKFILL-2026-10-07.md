# KCIF 공개 전환 재시도·본문 백필

작성: Codex 팀, 2026-10-07. 아래 운영 실행 절까지가 최신 결과이며 초기 구현 단계의 미실행 상태를 대체한다.

## 원인과 조사 범위

10/6 카탈로그 6건 중 916~919 네 건은 `restricted`, 920은 XLSX 본문 추출 완료이나 하이라이트 패턴 없음, 921은 PDF 하이라이트 정상이다. 37570 공개 다운로드 GET 한 건은 83바이트 `권한이 필요한 서비스 입니다.` 스크립트를 반환했다. 나머지 세 건은 동일 크기 오류 로그 및 DB 상태로 확인했고 직접 재조회하지 않았다. Claude/GPT 실패와는 별개의 수집 권한·표시 문제다.

사용자가 일정 기간 뒤 공개되는 자료의 재확인과 과거 미수집 백필을 승인했다. 권한 우회·로그인 자격증명 탐색은 하지 않는다. 기존 보고서는 재생성하지 않고, 새로 확보한 과거 본문을 이후 일간 브리프와 토픽 증분 입력으로 전달한다.

## 구현과 제한

- `kcif/download_retry.py`: 제한·실패·오래된 pending을 처음에는 발행 7일 경과 후 시도한다. 최근 pending은 기존 우선 경로에 남긴다.
- 정규 `_crawl_and_ingest`: 과거 최대 10건, 신규 포함 전체 최대 50건. 최근 FAILED 초기화에서 아직 cooldown 중인 자료를 제외한다. 신규·최근 다운로드의 일시 오류는 1일 뒤 다시 시도하며, 과거 공개 전환 재시도에만 7/14/28/30일 대기를 적용한다.
- 새 `kcif_download_attempts`: 시도 횟수, 마지막 시각, 다음 시각, 마지막 상태, 최초 파일 확보 시각. 재실패 대기는 7/14/28/30일. 미시도 자료 우선 후 마지막 시도 순으로 순환하여 오래된 미수집의 기아를 막는다.
- 원래 `published_date`는 변경하지 않는다. `available_ts`는 파일을 내려받은 시각이며, `report_texts.created_ts`는 본문이 실제로 추출·적재된 시각이다. 둘은 다를 수 있다.
- 과거 재시도는 공개 view에서 다운로드 링크를 다시 찾는다. 기존 PDF/XLSX와 이름이 겹쳐도 기존 원본을 덮어쓰지 않도록 별도 staging 후 report 번호·내용 hash 접두어로 보관한다.
- 일반 HTML·불완전 응답·네트워크 오류를 접근제한으로 영구 분류하지 않는다. 알려진 권한 응답/401/403은 기존 restricted 계약, 나머지는 FAILED 경로다.
- 본문 추출 실패가 이미 성공한 파일 다운로드를 FAILED로 되돌리지 않는다. 다음 정규 추출 단계가 md 없는 downloaded 자료를 재시도한다.

## 수동 명령

정본 경로에서 `uv run indepth kcif public-backfill --limit 10`.

기본 10건, 수동 1회 상한 117건(이번 승인된 전체 백로그 상한). 10건씩 선택하고 각 문서 시도 뒤 0.7~1.2초 대기한다. HTTP429는 즉시 중단, 연속 HTTP5xx 또는 TransportError는 세 건에서 중단한다. 일간 파이프라인과 같은 `kcif_daily.lock`을 비차단 배타 잠금하며 충돌 시 진행하지 않는다.

잠금 후 `references/.kcif-backfill/{시각}-{고유값}/`에 0600 SQLite backup과 manifest를 먼저 기록한다. manifest는 기존 보고서 hash·DB 파일 상태·진행 결과만 포함하며 본문과 자격증명을 복제하지 않는다. 기존 일간 보고서 파일은 변경하지 않는다. 백업은 원문 DB이므로 비공개 로컬 보존한다.

일간 신규 본문 delivery baseline은 backup 뒤, 신규 추출 전에 `store.initialize_daily_text_delivery()`로 초기화한다. 기존 804건이 새 자료로 한꺼번에 노출되는 것을 막는다. 실제 공개 권한 전환 여부는 재요청 결과로만 판단한다. 10/6 네 건은 아직 7일 경과 전이라 이번 즉시 백필 대상이 아니다.

수동 백필은 수집·본문 추출만 수행한다. Claude/GPT 호출, 임베딩 생성, 토픽 LLM 갱신, 보고서 재생성, 외부 발행은 하지 않는다. 다음 정규 daily 실행은 수정된 Python 모듈을 새 프로세스에서 읽는다. 이미 실행 중인 프로세스에 코드가 주입되는 것은 아니다.

## 일일 전달·토픽·추출 안전장치

- `kcif_daily_text_cursor`의 최초 기준점은 기존 본문 최대 ID 804, `kcif_daily_text_delivery`는 실제 수록한 본문 ID와 보고서 날짜를 기록한다. 파일 저장에 성공한 뒤에만 수록 처리한다. 동일 날짜 재생성에서는 같은 자료를 유지하고 다음 날짜에는 중복 노출하지 않는다.
- `뒤늦게 확보된 KCIF 원문` 섹션은 원발행일을 명시하고 하루 최대 30건을 싣는다. 남은 자료는 다음 실행까지 보존한다. 새 과거 본문이 있으면 평일 카탈로그 0건만으로 휴일로 판단하지 않는다. 주말에는 기존 쉼 정책을 유지하고 다음 평일로 이월한다.
- 기존 토픽의 본문 적재 ID 워터마크를 사용하므로 늦은 본문도 증분 후보가 된다. 과거 후보일 때만 현재 요약과 원발행일·최신 상황 보존 지시를 추가한다. 인용 자료 발행일과 사건일이 맞지 않으면 근거·이벤트·요약·워터마크 저장 전에 중단하고 실행 상태에 재시도를 표시한다. 전체 타임라인의 날짜·공백 정규화 제목이 정확히 같은 이벤트는 추가하지 않는다.
- 최신 요약의 의미적 정확성이나 표현이 다른 의미상 중복까지 자동 보증하지 않는다. 실제 토픽 LLM을 이번 작업에서 실행하지 않았다. 정규 daily의 기존 공급자 순서·섀도 정책도 이번 백필 작업으로 바꾸지 않았다.
- 교차검수에서 기존 추출기의 두 결함을 발견해 수정했다. `md_path`와 본문을 같은 트랜잭션으로 저장하며, 이미지뿐인 PDF는 본문 추출 성공으로 처리하지 않는다. 파일은 보존하고 OCR은 호출하지 않는다. 경로만 남고 본문이 없는 중간 실패 상태도 다음 추출에서 복구한다.

## 재개와 한계

남은 65건은 다음 재시도 시각이 된 것부터 정규 작업이 순환 확인한다. 즉시 다시 같은 명령을 실행해도 cooldown 중인 자료를 중복 요청하지 않는다. 사용자가 합법적으로 확보한 원문을 제공하면 별도 매칭·적재할 수 있지만 이번 작업에 그런 파일 입력은 없었다. 새로 열린 시점을 실시간 탐지하는 시스템은 아니며 재확인 주기만큼 지연될 수 있다.

후속 운영 확인은 다음 정규 daily 로그의 다운로드/추출/토픽 상태와 신규 과거 자료 섹션이다. 이 검증을 위해 `daily --force`나 `topics resummarize`를 실행하지 말 것. 과거 리포트를 다시 쓰거나 현재 요약의 품질 검수를 건너뛰는 근거로 백필 성공 건수를 사용하지 말 것.
